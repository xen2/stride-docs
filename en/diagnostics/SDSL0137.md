# Diagnostics Error SDSL0137

> {0} and {1} are both in phase {2} of {3} and {4}, and nothing orders them. Add [MixinOrder(After = {0})] to {1}, or this block to the effect: extend shader {5} { [MixinOrder({0}, {1})] {6}; }

In a composition:

> {0} and {1} are both in phase {2} of {3}, in a composition, and {4}, and nothing orders them. A block of the effect doesn't reach a composition: add [MixinOrder(After = {0})] to {1}, or give one of them a phase of its own, such as [Phase(Vendor.Later, After = {2})].

Reported by the shader compiler since Stride 4.5.

## Explanation

Two overrides of an [extension point](../manual/graphics/effects-and-shaders/shading-language/extension-points.md) are in the same phase, and their order changes the result, and nothing says which one comes first. The message says why:

- **They share a stream, which one of them writes.** Streams with one semantic count as one stream, and a store to the whole of `streams` writes every stream.
- **They share a field of an `inout` or `out` parameter of the point, or of a module `static`, which one of them writes.** A read or a write of the whole struct counts for every field. Two fields of one struct are two places. A parameter by value is the override's own copy, so it never counts.
- **They both have a side effect:** a write to a buffer or a texture, an atomic operation, a `discard`.
- **They wrap each other.** Each override of an `around` point wraps the rest, so two of one phase always need an order.

An effect built by the asset compiler has to state the order. In a mix built at run time, the order of the mixins decides, and the log gets one information line.

## Example

The following example generates SDSL0137:

```cs
module MyPipeline
{
    stream float Value;

    [Phases(Steps)]
    pipeline void Run() {}
};

module StepA
{
    import MyPipeline;

    [Phase(Steps)]
    override void Run()
    {
        base.Run();
        streams.Value = 1;
    }
};

module StepB
{
    import MyPipeline;

    [Phase(Steps)]
    override void Run()
    {
        base.Run();
        streams.Value = streams.Value * 2;
    }
};
```

The following example doesn't generate SDSL0137:

```cs
module StepB
{
    import MyPipeline;

    [Phase(Steps)]
    [MixinOrder(After = StepA)]
    override void Run()
    {
        base.Run();
        streams.Value = streams.Value * 2;
    }
};
```

The same applies to a struct that the point takes as `inout`. This pair generates SDSL0137, because both change `s.roughness`. If the second one wrote `s.metalness`, it wouldn't:

```cs
[Phase(Detail)]
extend MaterialPoints.Surface(inout MaterialSurface s)
{
    s.roughness = lerp(s.roughness, 0.1, 0.5);
}

[Phase(Detail)]
extend MaterialPoints.Surface(inout MaterialSurface s)
{
    s.roughness = lerp(s.roughness, 0.9, 0.5);
}
```

## Solution

Add `[MixinOrder(After = ...)]` to the override that has to run second, or put the two overrides in different phases. When you can't change the shaders, add the [block](../manual/graphics/effects-and-shaders/effect-language.md#blocks) of the message to the effect, also from another project with an `extend effect`:

```cs
extend shader MyPipeline { [MixinOrder(StepA, StepB)] Run; }
```

A block doesn't reach a composition. In a composed node, use `[MixinOrder]`, or a phase that one of the two adds: `[Phase(MyLibrary.Later, After = Detail)]`.
